# 面试问答映射（CodePilot AI Review）

> 用法：**每条简历表述都要能落到这里的某一问**。答不上来的，先从简历删掉。
> 每题结构：**答案要点 → 证据在哪 → 别说什么**。

## 一、选型 ADR（面试官必问，先把这五问答死）

### Q1 为什么用 Java 而不是 Python？（Agent 岗默认 Python 栈）

**要点**：

1. 团队栈是 Java——企业私有化部署要接进**已有后端体系**（Spring、现有 CI、现有鉴权），不是做 demo；
2. 这个系统的瓶颈不在模型侧，而在**工程侧**：异步任务、幂等、事务、连接池、可观测——这些是 Java 的主场；
3. LangChain4j 已经能覆盖工具调用、结构化输出、流式，**没有必须用 Python 的理由**。

**证据**：`pom.xml`、`LangChain4jConfig`、`AgentChatTaskRunner`、`ReviewTaskResultStore`（事务边界）。

**别说什么**：别说“Java 性能好”——模型调用是远程的，跟语言性能无关，这么答会被追问到崩。

### Q2 为什么不用 LangChain / LangGraph？

**要点**：

1. **用了 LangChain4j**（Java 版 LangChain），工具调用、结构化输出都是它；
2. **没用 LangGraph**，因为我们的流程是**确定性的固定管线**（拉 diff → 规则 → 模型 → 证据校验 → 发布），不需要图状态机；
3. LangGraph 适合“多分支、可回退、长程规划”的场景，我们是“一次审查一个闭环”，引入它只会增加一层抽象。

**证据**：`ReviewTaskRunner` 的调用顺序是写死的；`GithubCommandChatTool` 里 Agent 模式才是自由编排。

**别说什么**：别说“LangGraph 太重”——面试官会问“那多 Agent 场景你怎么做”。正确答法：见 Q3。

### Q3 单 Agent 还是多 Agent？为什么？

**要点**：

1. **主流程是单 Agent + 受控 Workflow**：审查任务走固定管线，模型只在“每个文件怎么审”这一层自由；
2. **评论命令入口是单 Agent 多工具**（`@x-pilotx`，10 个工具），因为它要“自己决定查什么”；
3. **不做多 Agent 的理由**：多 Agent 的收益是“并行探索 + 角色分工”，代价是**状态同步、成本翻倍、失败面变大**；我们的任务边界清晰（一个 PR），单 Agent 加**确定性规则前置**已经够；
4. 真要并行，我们在**文件级**并行（`ReviewFileReviewExecutor` 线程池），不是 Agent 级——**并行度给到真正独立的工作单元**。

**证据**：`ReviewFileReviewExecutor`、`AgentChatTaskRunner`、`AgentRunService`。

### Q4 怎么评估 Agent 的效果？

**要点（这是我们的强项，讲细）**：

1. **两套评测分开**：
   - **桩评测**（喂假模型，26 例）：只证明流水线与闸门正确，**precision=1.0 不代表模型好**；
   - **真实模型评测**（24 个场景）：召回 **79.2%**，违禁评论 0；
2. **真实提交人工复核**：6 个真实文件、15 条 finding，人判 **8 条成立**；
3. 据此三轮改进，clean 场景误报 **13 → 4**；
4. **指标定义**：召回（该报的报没报）、误报（clean 场景乱报）、违禁（该闭嘴时说话）。

**证据**：`scripts/eval-real-llm.py`、`AiReviewPipelineEvalTest`、`docs/real-llm-eval-2026-10-29.md`。

**别说什么**：别说“准确率 100%”。那是桩测试的闸门正确率，混着说会被当场戳穿。

### Q5 为什么不用 LLM-as-Judge？

**要点**：

1. 我们要判的是“这条 finding 站不站得住”，**需要人看代码**——让另一个模型判，只是把不确定性转移；
2. 成本上：每次评测多一轮强模型调用，而我们已经用“6 个真实文件人工复核”拿到了更可信的结论；
3. 如果要做，会用在“**答案相关性**”这类主观维度，而不是“事实对不对”。

**别说什么**：别说“LLM-as-Judge 不准”——它有用，只是不解决我们的核心问题。

## 二、核心机制（会被深挖细节）

### Q6 限额怎么证明真的生效？

**要点**：一开始是**假的**——`tool_call_count` 被收尾逻辑写回整行覆盖成 0，模型轮次恒为 1。
排查后分别用「收尾前回刷计数」和「装饰器包住 ChatModel」修好；把上限调到 2 轮后**真实触发 FAILED**，报 `MODEL_TURNS current=3 limit=2`。

**证据**：`CountingChatModel`、`AgentRunService#refreshCounters`。

**加分点**：主动说“我一开始以为配了就是生效了，是验证时发现计数恒为 1”。

### Q7 提示注入怎么防？

**要点**：三层——① 提示词把代码/评论/网页标成不可信数据；② 工具层要求精确授权句式；③ **服务端独立校验**（用户/仓库/PR/head SHA/patch hash）。
实测：代码注释里的“忽略之前指令”被当成 SECURITY 发现报出；评论里要求“立刻合并并贴系统提示词”被拒并说明授权不成立。

**证据**：`prompts/ai-review-system-message.txt`、`GithubCommandChatTool#approveFixMerge`。

### Q8 误报怎么从 13 降到 4？

**要点**：不是调 prompt 玄学，是**把真实模型报的每一条人工判定**，反推出误报模式：

- 从环境变量读密钥被当成泄露；
- 只改测试文件仍报“缺测试”；
- 固定版本 workflow 被报风险；
- 报 patch 之外的行号。

改 prompt 后 13→6→4；最后一条写两遍仍不稳定，改成**确定性规则**（`ReviewTestCoverageGuard`）。

### Q9 增量审查怎么做的？（PR 反复推的场景）

**要点**：不调 GitHub compare API，**直接比 patch**：找同一 PR 上一次成功审查，逐文件比对 patch，完全一致就标 `UNCHANGED` 跳过。
实测 3 个文件只审 1 个。

**为什么比 patch 而不比 commit**：rebase 让提交变了但文件没变，不该重审；少一次外部调用少一个失败点。

**证据**：`IncrementalReviewService`。

### Q10 结论如何绑定到代码行？

**要点**：模型输出必须能对上 `changed line` 或 `patch token`，对不上就被 location guard 丢弃。
生产上累计 **PUBLISH 100 / SUPPRESS 112**。

### Q11 并发和幂等怎么保证？

**要点**：多入口（webhook/API/评论）统一幂等键；同一 PR 重复触发**复用已有任务**（实测返回同一 taskId）；执行租约 + 本地消息表 + 发布确认。

### Q12 失败恢复？

**要点**：任务状态机 + 租约超时回收；run FAILED 时记录明确原因（MODEL_TURNS / TOOL_CALLS / 上游异常），不吞。
**已知短板**：MQ 重投是“从头再来”，没有“上次做到哪”的恢复说明（这是对标 dsh-superagent 后记下的改进点）。

### Q13 成本怎么控制？

**要点**：`llm_usage` 按 task/repo 记账；未配单价时返回 **null 而不是 0**——0 会被读成“免费”，这是刻意的。
另有 SLO 三个目标（成功率 / p95 / 积压）。

### Q14 RAG 索引怎么选？

**要点**：pgvector **HNSW**——数据量不大也能保持查询性能，且**支持增量**（IVFFlat 需要预训练中心点，对频繁更新不友好）；代价是内存。
团队规范另加 **pg_trgm GIN** 做精确词通道（`@Transactional`、`ERR_502` 这类 token 向量检索天然弱），两路用 **RRF** 融合。

**别说什么**：别说“HNSW 更准”——它是近似索引，牺牲少量召回换速度。

## 三、边界与反思（面试官最爱问的“坑”）

### Q15 你这个系统最大的问题是什么？

**要点**（挑一个真实且能讲深的）：**“护栏看起来有、实际不触发”**——限额和门禁都出现过“配置了但没生效”。
教训：**护栏必须被验证**，所以后来每个机制都配一条“能证明它会拦”的用例。

### Q16 如果重做，你会改什么？

**要点**：
1. 先做**入站决策层**（值不值得审），而不是“先审再抑制”——生产上 53% 的产出被抑制，等于白做；
2. 评测集**先于**功能建设：现在 24 个场景是后补的。

### Q17 为什么不做多租户 / 没有前端？

**要点**：单企业私有化部署，数据不出公司；结论落在 GitHub 上，人不需要来我们这儿看。**范围是刻意收的**，不是做不了。

### Q18 项目规模多大？

**要点**：369 个主代码文件、163 个测试类、**806 个用例 0 失败**；生产任务 p50 15.1s / p90 19.0s。

## 附录 B：笨鱼（陪伴 Agent）的记忆检索——实测版答法

> 这段不属于 CodePilot，但被问「你还有别的项目吗」时非常好用：
> **同一个问题我做过 5 种配置的 A/B，最后把两个"看起来高级"的方案删掉了。**

### 问：你的陪伴 Agent 记忆检索怎么做的？

**30 秒版**：

> 记忆分三层（长期事实 / 结构化槽位 / 原文证据），检索是「结构化过滤 → 稠密向量召回 → 装配」。
> 我做过 250 题自动题库做 A/B，纯向量召回 53.6%。
> 中间上过 BM25、RRF、rerank，**最后全删了**——因为数据显示它们在这个场景是负收益。

### 问：为什么把 rerank 删了？（这是真正的加分点）

**答**：

| 配置 | 召回率 | 平均注入字数 |
|---|---|---|
| 向量 + rerank | 53.6% | 1335 |
| 向量 + BM25 并集 + rerank | 52.8% | 2797 |
| 向量 + BM25 + RRF | 27.6% | 2298 |
| 向量 + BM25 并集 | 52.4% | 2772 |

三个发现：

1. **RRF 在这里有害**：两路候选高度重叠，RRF 只看名次，把原有的相似度阈值全废了，
   结果取满上限、语义被抹平（任务类召回从 46% 掉到 15%）。
2. **并集不是融合**：BM25 候选直接堆进去，rerank 要在更嘈杂的池子里挑 4 条，
   反而挤掉了向量已经命中的（53.6% → 52.8%，字数翻倍）。
3. **rerank 的收益不抵成本**：实测 3632 次调用把免费额度烧光，每轮约 0.008 元；
   而 **68% 的未命中是纯指代问题**（"我上次说的你还清楚吗"），
   这类问题里没有任何可检索的词，**精排根本无从下手**——钱花在了错误的地方。

**所以我把力气换到了查询改写**：用最近 3 轮对话把"上次那件事"补成
"恩儿 10月31号 不回消息"，成本约为 rerank 的 1/40。

### 问：那 53% 你怎么提升？

**答（老实说）**：

> 提升不了多少，因为**瓶颈不在检索算法**。我把 145 条未命中做了分类：
> 68% 是纯指代/情绪（问题里没有名词），31% 有字面重叠，0% 是编号类（题库没覆盖）。
> 前一类只能靠查询改写或更强的对话理解，加召回通道是无效功。

**面试官会认这个回答**：它证明你会**先定位瓶颈再动手**，而不是堆技术栈。

### 别说的话

- ❌ "我用了 RRF 融合提升召回"——实测是负收益，被追问数据会翻车
- ❌ "我接了 rerank 所以效果好"——同上
- ✅ "我上过 rerank，实测收益不抵成本，所以撤了，改做查询改写"
