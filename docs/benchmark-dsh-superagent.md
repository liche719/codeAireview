# 外部对标：DeepSeek dsh-superagent（2026-11-02）

> 对象：[deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)（MIT，2026-10-31 开源的研究原型）
> 定性：**研究代码，不是产品**。官方自己写明"可能仍有 bug、工程规范不一致"。

## 一句话对比

| | dsh-superagent | CodePilot |
|---|---|---|
| 角色 | **生产者**：接单写代码 | **守门人**：审别人的代码 |
| 关注指标 | 任务吞吐、自主性 | **误报率**（宁可少说，不能说错） |
| 失败代价 | 代码没写完 | 挡住一次正常合并 → 团队撤掉门禁 |
| 规模假设 | 一个仓库、多来源接单 | 单组织几十仓库、日增几十 PR |

所以**整套状态机搬过来是过度设计**，但它对"注意力"的处理值得抄。

## 值得借鉴的五点（按性价比排序）

### ① 有"要不要做"的决策层（Eval）——最值得做

它的链路：

```
Trigger（GitHub/飞书来消息）
  → Eval：模型评估 接受/停/忽略/**不可用**，带 deadline，过期 requeue
  → Ticket（任务，带授权依据 Mandate）
  → Assignment（执行）→ Report
```

**关键**："不可用"会记成待人处理的 problem，而不是静默失败。

我们现在是 webhook 进来**直接建任务**，没有判断层。导致：重复 PR、极小改动、已审过的 SHA 也照样跑一次全套模型审查。

**可落地的形态**：审查前加一次轻量决策，记录 decision + reason，不值得就不建任务。

### ② 每条外发消息都有"目的"

它定义四种：`acknowledgement` / `answer` / `result` / `attention`，各有放行规则，ack 限 100 词。

我们只有 `PUBLISH/SUPPRESS` 两级，没有"这条消息是为了什么"。加上 purpose 后，"为什么发这条评论"变成可查询、可审计的事实。

### ③ "等人类处理"是一等公民

它有一个专门的面板视图（unavailable / blocked / attention）。我们的 gate 状态、审批、失败散落在各处。

### ④ 重启恢复带"恢复说明"

中断后重新拉起 Assignment 时会带一条 recovery note（上次做到哪）。我们是 MQ 重投，语义等于"从头再来"。

### ⑤ 策略版本化

`policyVersion` 参与评估；改规则后只通知**受影响的**任务、在途评估重启。
我们改阈值后，没有"这条任务是按旧规则判的"这回事。

## 明确不抄的

| 它的设计 | 为什么不抄 |
|---|---|
| Ticket / Eval / Disposition / Thread 四张表状态机 | 它要处理"一个仓库多人多轮接单"；我们的审查是一次闭环 |
| 13 个 orchestrator 工具 + 角色分权 | 我们 10 个工具够用 |
| SQLite + 生成列 + KV | 已经是 Postgres |
| Executor 独立工作目录 | 那是"写代码"的隔离需求；我们只读 diff |

## 建议的落地顺序

| 步骤 | 内容 | 成本 | 怎么验证 |
|---|---|---|---|
| 1 | **决策层**：审查前判断"值不值得审"，记 decision + reason | 中 | 任务数下降多少、误报率变化 |
| 2 | **消息目的**：外发评论带 `purpose`，按目的决定发不发 | 小 | 评论数与"无意义评论"比例 |
| 3 | 待人处理清单：把 blocked / unavailable / 失败聚成一个接口 | 小 | 面板一列 |
| 4 | 恢复说明：中断任务重投时带上"上次做到哪" | 中 | 重启后任务重复执行的次数 |

**第 1 步最值**：现在的链路是"先审出来 → 再抑制"（PUBLISH 100 / SUPPRESS 112），
等于 **53% 的审查产出是白做的**。决策层省的是整次模型调用，不只是评论。
