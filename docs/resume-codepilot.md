# CodePilot AI · 简历条目与面试口径（2026-10-29）

> 所有数字都来自本项目实测，来源写每条后面。**没有测过的不要写**。
> 关键纪律：**mock 评测与真实模型评测必须分开说**——这是这个项目最容易被问穿的地方，也是最能体现工程判断力的地方。

---

## 一、项目定位（简历开头一行）

> **CodePilot AI｜GitHub PR 智能审查系统（Java 21 / Spring Boot / RabbitMQ / PostgreSQL+pgvector / Redis / LangChain4j）**
> 把一次 PR 审查做成可异步调度、可并发、可验证证据、可回写 GitHub 的流水线；支持 Webhook / API / 评论命令多入口，
> 以及由模型自由组合查询、RAG 与联网能力的 Agent 模式。**797 个自动化用例 0 失败**。

---

## 二、四条核心条目（选 3~4 条放简历）

### ① 任务链路与幂等

> 统一 Webhook / 手动 API / PR 评论命令入口，按 `owner/repo/pr/headSha` 做 Redis 去重与任务复用；
> 本地消息表 + RabbitMQ 发布确认 + 执行租约与原子抢占，保证异步任务**不重复执行、宕机可恢复**。

**面试展开**：为什么不用"消费即删"（宕机会丢）；租约如何解决"消费者假死"；重复 webhook 如何不产生第二条评论。

### ② 审查质量：规则在前，模型在后

> LLM 前强制执行 SQL 风险 / 敏感信息 / 缺测试等确定性规则，团队规范经 pgvector 召回注入；
> 模型输出必须绑定 changed line、patch token 或审查计划证据，否则被 patch verification / location guard 剔除。

**实测**：真实提交上模型报 15 条，人工复核 **8 条成立**（见下）。

### ③ 用真实模型量化质量（这个项目最值钱的一条）

> 发现原有评测用**回放固定模型输出**，`precision=1.0` 只证明流水线与闸门正确、不证明模型审得好；
> 因此另建真实模型评测：26 个标注场景 + 真实提交样本，跑出 **召回 79.2%、违禁评论 0、clean 场景误报 4 条、单文件耗时 p50 3.2s**，
> 并据此做了三轮 prompt 与一条确定性规则的改进（误报 13 → 4）。

**必须会讲的口径**：
- mock 评测 100% ≠ 模型准确率；
- 真实模型 79.2% 是"跳过 3 个闸门用例"后的召回，闸门用例（坏 JSON、删除行可评论性）不适用真模型；
- 真实提交上"8/15 条成立"，不是"准确率 53%"——那些提交不是标准答案，判定是人工的。

### ④ 运营可观测

> 补了一个时间窗口的运营指标接口 `GET /api/stats/review?days=7`：任务成功率、耗时分位、失败类型分布、
> 发布成功率、队列积压，一次查询答完；生产实测 p50 15.1s / p90 19.0s、成功率 90.9%、问题级发布率 47.2%。

**为什么不用 Prometheus**：现有部署只有 Actuator 的累计计数器，没有历史曲线；这个接口用主库算窗口指标，
不引入新组件，且"积压"用"PENDING 任务数 + 最老等待时长"表达，比队列深度更贴近用户感受。

## 三、面试预判问题

| 追问 | 答法要点 |
|---|---|
| 你的 recall 100% 怎么来的？ | **不硬撑**：那是 mock 回放的闸门测试；真实模型是 79.2%，mock 与真实分开量 |
| 为什么要两套评测？ | mock 测的是"流水线与闸门对不对"（回归用），真实模型测"模型在这个 prompt 下审得好不好"（质量用）。混在一起谈就是自欺 |
| 误报怎么降的？ | 拿真实评测的具体误报反推：环境变量读密钥不是泄露、只改测试文件不报缺测试、固定版本 workflow 不算风险、diff 是片段不能报编译错误。13 → 4 |
| 有一条 prompt 治不好怎么办？ | `TEST_MISSING` 那条写了两遍提示词仍不稳定 → 改成**确定性规则**：PR 里已有同名测试就直接丢弃，5 条单测锁着。**能确定的事交给规则** |
| 怎么证明不是 demo？ | 797 用例、真实提交评测、生产任务记录、指标接口的实时数据；以及**明确说出现在缺什么**（评论回写需要 token） |
| 最大的坑是什么？ | 部署后才发现：`@PostConstruct` 带参数导致启动即崩（那个 bean 在测试里被条件关闭，从没被创建过）；DeepSeek 不支持 `response_format` 导致每次 LLM 调用静默降级 |

## 四、现在的诚实边界（主动说，反而加分）

1. **PR 评论回写没有端到端证据**：部署里的 GitHub token 过期，目前只能验证到"任务 SUCCESS、问题落库"；
   回写评论需要有效凭据，这一步**没做**。
2. **真实提交样本只有 6 个文件**：不足以谈统计显著性，只能谈"这 15 条里 8 条成立"。
3. **评测用例是手写的**：代表性有限，还没有真实脱敏 PR 数据集。

## 五、可复现命令（面试官要看现场跑）

```bash
# 真实模型评测（合成场景）
python scripts/eval-real-llm.py --out report.json

# 真实提交评测（固定同批，便于 A/B）
python scripts/eval-real-prs.py --revs <sha1>,<sha2> --limit-files 2 --out real.json

# 生产指标
curl -s -H "X-CodePilot-Api-Key: $KEY" "https://liche.cloud:8990/api/stats/review?days=30"
```

## 六、和「笨鱼」的分工：不要讲成同一个故事

两个项目都是 Agent，但**卖点必须错开**，否则面试官会问"这不就是同一个项目换了个壳"。

| 维度 | 笨鱼（QQ 长期陪伴 Agent） | CodePilot（PR 审查） |
|---|---|---|
| 核心问题 | **记得住、聊得像人、不卡** | **AI 说的话能不能信、任务能不能可靠跑完** |
| 记忆 | 三层记忆、取代链、证据级联（深） | finding 记忆 + 跨 headSha 去重（浅，但服务于去重） |
| 工具 | 65 个工具的调用循环、按需披露、失败反思、幂等键 | 工具是配角；主角是**确定性规则 + 证据绑定** |
| 可靠性 | 单轮内：超时归"结果未知"、同参重复检测 | 跨进程：RabbitMQ + outbox + 执行租约 + 原子抢占 |
| 交互 | 流式、首句提前下发、语音时序、进度条 | 评论形态：摘要 / 行内 / suggestion / 去重 marker |
| 评测 | 记忆 28 例 + Agent 19 例（任务级多轮） | mock 闸门 26 例 + **真实模型 24 例 + 真实提交人工复核** |
| 一句话 | 「它记得住你」 | 「它说的话有证据」 |

**在简历里的分工措辞**：
- 笨鱼 → "长期记忆与交互体验"（它的记忆设计是别处看不到的）
- CodePilot → "AI 输出的可信性与异步工程"（它的证据绑定与任务可靠性是别处看不到的）

**面试时千万别说成一样的**：
- 别在 CodePilot 里大讲"工具调用循环 + 失败反思"——那是笨鱼的主场；
- 别在笨鱼里大讲"RabbitMQ 可靠性"——那是 CodePilot 的主场。

## 七、CodePilot 可以讲什么（六条，按"别人抄不走"排序）

1. **AI 输出的证据绑定**：模型报的每一条必须能落到 changed line / patch token / 审查计划证据，
   落不到就丢；这不是"再加一层校验"，而是把"可信"当成产品契约。
2. **评测方法论**：发现原评测是回放假模型 → 另建真实模型评测 → 再用真实提交做人工复核
   （15 条里 8 条成立）→ 据此改 prompt 与规则（误报 13→4、违禁 4→0）。
   这套"先证伪自己的指标"的过程，比任何一个数字都值钱。
3. **触发与执行解耦**：Webhook / API / 评论命令多入口 → 任务落库 → 本地消息表 + 发布确认 + 执行租约，
   宕机可恢复、重复触发不重复执行（实测：同一 PR 再触发返回的是已有任务）。
4. **确定性规则先于模型**：SQL 风险 / 敏感信息 / 缺测试等规则在 LLM 之前执行，
   不依赖模型"主动想起"；模型报的问题与规则结果再去重合并。
5. **评论生命周期**：marker 指纹去重、摘要幂等更新、行内评论定位守卫、维护者 dismiss 同步、
   跨 push 的 finding 状态机。
6. **运营可观测**：时间窗口的成功率/耗时分位/失败类型/发布率/积压，一次查询答完（`/api/stats/review`）。

## 八、不能讲的（面试官一追问就露馅）

| 不能讲 | 真相 | 可以怎么讲 |
|---|---|---|
| "precision 100%" | 那是 mock 回放的闸门测试 | "mock 测闸门，真实模型 79.2%" |
| "增量审查" | **没做**（全局搜索 `incremental` = 0） | "目前是全量审 + finding 记忆抑制重复" |
| "多租户 SaaS" | 单部署、单账号 | "单实例部署，GitHub App 多租户在设计里" |
| "线上很大的量" | 生产任务累计十几条 | "沙箱 PR 端到端验证 + 797 用例回归" |
| "误报很低" | 真实提交上 15 条里 7 条是误报 | "误报集中在'看不到被调用方'，已用确定性规则挡掉一类" |
| "支持所有语言" | 定位是 Java / Spring Boot | "面向 Java/Spring Boot 团队" |

## 九、两个项目放在一起的一句话总结（终面用）

> 一个解决「**记住你**」，一个解决「**说话算数**」——
> 前者是长期记忆与交互体验，后者是证据绑定与异步可靠性；
> 两个项目我都坚持同一件事：**先证明自己的指标是真的，再谈优化**。
